Lazarusチャレンジ2日目です。今回は、前回作成したカエルの歌のMIDIファイルを実際に再生できるMIDIプレイヤーを作成することにしました。

今回の目標

Day1でMIDIファイルを作成するアプリを完成させましたが、作成したMIDIファイルを再生する手段がありませんでした。そこで今回は、以下の機能を持つMIDIプレイヤーを開発することにしました：

  • MIDIファイルの再生機能
  • Trackbarによる再生位置の調整
  • 再生、停止、一時停止の操作
  • メニューからの操作
  • ファイルを開く機能

前回作成したカエルの歌を、自分で作ったプレイヤーで再生できるようになるのが目標です。

プロジェクトの作成

まずはLazarus IDEを開いて、新規プロジェクトを作成します。

  1. Lazarus IDEを起動
  2. 「ファイル」→「新規プロジェクト」を選択
  3. 「アプリケーション」を選択してOK
  4. プロジェクト用のフォルダを作成し、lprファイルとunitファイルを保存

プロジェクトの準備ができたら、Cursorでフォルダを開いて開発を進めます。Cursorを使うことで、AIの力を借りながら効率的にコーディングできるはずです。

Geminiの解説

ご提示いただいたコードで「一音（あるいは一瞬）しか再生されない」という現象が起きる最大の原因は、**TrackBar1Change イベントの再帰的な呼び出し（ループ）**にあります。

根本的な原因：無限ループ（シークの競合）

Geminiの解説によると、問題の流れは以下の通りです：

  1. Timer1Timer が実行され、UpdatePosition を呼び出します。
  2. UpdatePosition 内で、現在の再生位置に合わせて TrackBar1.Position := ... と値を書き換えます。
  3. すると、プログラムによって値が変わったにもかかわらず、TrackBar1Change イベントが発生してしまいます。
  4. TrackBar1Change 内で SetMidiPosition（MCIのシーク操作）が実行されます。
  5. 再生中にシーク操作（MCI_SEEK）を行うと、多くのデバイスでは再生が停止するか、あるいはシークした瞬間にまたタイマーが動いて位置を戻そうとするため、再生が極めて短時間で止まったり、冒頭に戻ったりしてしまいます。

結果として、「再生開始 → タイマー作動 → トラックバー更新 → シーク命令発行 → 再生停止」という流れが一瞬で起きています。

解決方法

この問題を解決するには、プログラムによるトラックバーの更新と、ユーザーによる操作を区別する必要があります。具体的には：

  • フラグ変数を用意して、プログラムによる更新中かどうかを管理する
  • プログラムによる更新時は、TrackBar1Change イベント内でシーク操作をスキップする
  • ユーザーがトラックバーを操作したときだけ、シーク操作を実行する

この方法により、タイマーによる自動更新では再生が停止せず、ユーザーが手動で位置を調整したときだけシークが実行されるようになります。

Geminiのコードの改善点

Geminiが提供してくれたコードには、以下の改善が含まれていました：

  1. フラグ変数の追加: FUpdatingPosition というフラグを追加し、プログラムによる更新中かどうかを管理
  2. UpdatePositionメソッドの改善: トラックバーを更新する前にフラグをTrueに設定し、更新後にFalseに戻す
  3. TrackBar1Changeイベントの改善: フラグがTrueのとき（プログラムによる更新中）はシーク操作をスキップし、Falseのとき（ユーザー操作）だけシークを実行

これにより、タイマーによる自動更新ではシーク操作が実行されず、ユーザーがトラックバーを操作したときだけシークが実行されるようになっています。結果として、再生が途切れることなく、最後まで連続して再生できるようになりました。

学んだこと

Day2の開発を通じて、多くのことを学びました：

AIツールの使い分け

  • Cursor: コード生成には便利だが、複雑な問題の修正には限界がある
  • Gemini: 問題の原因を詳しく解説してくれる。コードの解説や修正案の提示に優れている
  • 複数のAIツールを使い分けることで、より効果的に問題を解決できる

開発環境について

  • Cursorは便利ですが、生成されたコードをそのまま使うのではなく、実際に動作確認をすることが重要
  • Lazarusのフォームデザイナーでコンポーネントを配置する際は、表示状態を確認しながら進める必要がある
  • コマンドラインからのビルドは効率的だが、IDEでのデバッグも併用すべき
  • IDEを使う意味について考えさせられた。Cursorだけで開発できると思っていたが、フォームデザイナーなどIDEの機能はやはり必要

技術的な学び

  • MIDI再生の実装は思ったより複雑。一音ずつしか再生されない問題は、MIDIイベントの処理方法を見直す必要がある
  • イベント駆動型のプログラミングでは、イベントの再帰的な呼び出しに注意が必要
  • プログラムによる更新とユーザー操作を区別するフラグの重要性
  • ビルドコマンドのパス指定について、最初にフルパスを教えておくと、その後は短縮形で通じる。環境変数を汚さずに済む方法として有効

問題解決のプロセス

  • Cursorに修正を依頼しても、必ずしも期待通りに修正されるとは限らない
  • コードを自分で読んで理解しようとすることも重要だが、理解できない場合は別のAIツールに相談するのも有効
  • 問題の原因を理解できなくても、動くコードを手に入れることで先に進めることもある

Day2にして早くも複数の問題に直面しましたが、最終的には完成させることができました。メニューの問題もMIDI再生の問題も解決し、無事にMIDIプレイヤーが完成しました！

まとめ

Day2では、MIDIプレイヤーの開発を通じて、以下のことを経験しました：

  1. Cursorでのコード生成 - 最初のコードは生成されたが、問題が発生
  2. IDEでの修正 - メニューの設定など、IDEの機能が必要な場面
  3. Cursorでの再修正 - 修正依頼をしたが、期待通りにはいかなかった
  4. Geminiでの問題解決 - 問題の原因を解説してもらい、修正コードを取得

複数のAIツールを活用することで、最終的には問題を解決できました。AIツールは完璧ではないですが、適切に使い分けることで、効率的に開発を進められることがわかりました。
