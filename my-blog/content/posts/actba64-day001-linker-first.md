# 後ろから作る：リンカー → アセンブラ → コンパイラー - Day1

7/23 木曜日だ。今日も暑い日だ。このごろ夏の暑さは尋常ではないが、冷房の効いた部屋でパソコンに向かっていると、かえって余計なことを考え始める。

ふと「自作コンパイラを作ってみようか」と思い立ったのは、そんな夏の日のことだった。どうせやるなら、昔よく使っていた言語を自分の手で蘇らせてみたい。そんな無謀とも思える構想を胸に、まずは相棒となるAIに相談してみることにした。

## Gemini 

まず、Gemini に以下のように問う

**プロンプト**

>これはホビーのプロジェクトだが、昔activebasicという言語があって最終的にはactivebasicをactivebasicでセルフコンパイルできるようにしたい。まずは、何もないコードを入力すると何もしないexeを作る


**回答**

>ActiveBasic（AB）、めちゃくちゃ懐かしいですね！N88-BASICの文法を引き継ぎながら Win32 API や DLL をバリバリ叩けたあの名機（言語）ですか。しかも最終目標が「ActiveBasicによるSelf-hosting（セルフコンパイル）」とは、最高にロマンのあるホビープロジェクトです！


ActiveBasic が盛んだったころに、Gemini は影も形もなかっただろう。「懐かしい」というのは機械の感情からしてもおかしいだろうと突っ込みたくはなる。しかし、セルフコンパイルのための道筋を示してくれた。

## 最初の計画
- **フェーズ1**：アセンブラのコードを出力する ActiveBasic のコードを作成し、外部のアセンブラ（NASM など）とリンカ（GoLink など）を呼び出して EXE を作る。
- **フェーズ2**：代替として GCC（MinGW）等を経由して C 言語にトランスパイルして EXE 化する。
- **フェーズ3（最終形）**：外部ツール依存を無くし、自分で直接 PE（Portable Executable）ファイルを吐き出す。

後ほど説明するが、実際にはこの**真逆の手順**で開発がすすめられた。

## 何もしないで正常終了するプログラム

何もしないコード（空コード）から、何もせずに正常終了する最小の EXE（PE ファイル）を生成するプログラムを作成するにはどうすればよいだろうか。まず、何もしないで正常に終了するプログラムをアセンブラで考えてみる。

**sample.asm**

```nasm
global _main
extern _ExitProcess@4

section .text
_main:
    push 0                  ; 終了コード 0 (正常終了)
    call _ExitProcess@4     ; Windowsを正常終了するAPI
```

これが、出力すべき asm になる。ActiveBasic で作ったプログラムが上記の asm ファイルを吐き出せばよい。

```vb
' =========================================================
' ActiveBasic Self-Hosting Project - Phase 0
' 「何もしないコードからEXEを作るコンパイラ」
' =========================================================

#include <windows.sbp>

Function Main() As Long
    Dim srcPath As String
    Dim asmPath As String
    Dim exePath As String
    Dim hFile As Long

    srcPath = "test.ab"      ' 入力 (空のActiveBasicコード)
    asmPath = "output.asm"   ' 中間ファイル (アセンブリ)
    exePath = "test.exe"     ' 最終出力 (Executable)

    Print "コンパイル開始: "; srcPath

    ' 1. ソースコードの読み込み（今回は空かどうかを確認するだけ）
    ' ※将来的に構文解析（パーサー）をここに入れる

    ' 2. アセンブリコードの生成
    hFile = FileOpen(asmPath, "w")
    If hFile = 0 Then
        Print "エラー: 中間ファイルの作成に失敗しました。"
        Exit Function
    End If

    ' Windowsで「正常終了するだけ」のアセンブリ(NASM用)を吐き出す
    FilePrint(hFile, "global _main")
    FilePrint(hFile, "extern _ExitProcess@4")
    FilePrint(hFile, "section .text")
    FilePrint(hFile, "_main:")
    FilePrint(hFile, "    push 0")
    FilePrint(hFile, "    call _ExitProcess@4")
    FileClose(hFile)

    Print "中間ファイル生成完了: "; asmPath

    ' 3. アセンブル & リンク (外部ツールを呼び出し)
    ' 例: nasm.exe と golink.exe を使う場合
    Print "アセンブル&リンク中..."

    ' NASMで .asm -> .obj に変換
    Shell("nasm.exe -f win32 output.asm -o output.obj", 1)

    ' GoLinkで .obj -> .exe に変換 (kernel32.dllのExitProcessを結合)
    Shell("golink.exe /console output.obj kernel32.dll", 1)

    Print "ビルド完了: "; exePath
End Function

Main()
```

さきほどの asm を吐き出したあと、外部ツールを呼び出し、アセンブルとリンクを行う。

## 全部自作してしまおう

だが、作者はここで、このコードが NASM と GoLink を使っていることに違和感を覚えた。

せっかく作っても、実行に外部ツールがいるんだったらコンパイラーを作った意味があるのだろうか。ActiveBasic のように EXE まで作れなければ意味がない。

**アセンブラもリンカも全て自作してしまおう**という大胆な野望が脳裏に浮かんだ。そこで、

>まだ作らないがリンカとasmもactivebasicで作りたい

とプロンプトした。自分の中では、リンカーやアセンブラができて完全にセルフコンパイルできるのは遠い将来だと思っていたのだ。Gemini は

>将来実装するとき、挫折しないための裏技的で面白いステップがあります。それは「後ろ（リンカ）から順に作る」ことです。


と回答してきた。

じつは、機能を限定すればリンカーやアセンブラのほうが難易度は低いのだ。最初にコンパイラーから入ると、出力されるのは asm ファイルだ。asm ファイル自体は動かすことができない。リンカーやアセンブラを先に作っていけば、プログラムが動くのを実感できる。

### 1. リンカ（Linker）

リンカーは何をするものだろう？よくコンピューターは機械語しか読むことできないと聞かされてきた。AIで話は変わってきたが、それでも最終的には機械語のプログラムが動くことには違いない。
では、アセンブラが機械語に変換したら、それで実行可能になるのだろうか？実はアセンブルしたあとの機械語に対して、リンカがもう一仕事しなければならない。

- **リンカの役割**：`.obj` ファイル（COFF 形式）を読み込み、ヘッダーを整形して Windows が理解できる PE フォーマット（`.exe`）のバイナリに変換する。
- **主な仕事**：
  1. `.text`（コード）や `.data`（データ）などのセクションを連続したメモリ領域に配置する。
  2. `ExitProcess` などの外部 DLL 関数を呼ぶための Import Address Table（IAT）を構築する。
  3. 各命令の参照アドレスを書き換える（アドレス解決 / リロケーション）。

アセンブラ→COFF→リンカ→PE(.exe)
というパイプラインになる。

実は、アセンブラよりもリンカの方が構造が単純で作りやすい。まず、最初に作るものとしてリンカー（**ablinker**）を作成することにした。

### 2. アセンブラ（Assembler）

リンカーの次に作るのはアセンブラだ。アセンブラは、テキストで書かれたアセンブリ言語を 1 対 1 でマシン語（バイナリ）に変換し、COFF（`.obj`）形式で吐き出す。

- **役割**：`push 0` や `call _ExitProcess` というテキスト命令を、`6A 00` や `E8 xx xx xx xx` といった x86 のバイト列に置き換える。
- **主な仕事**：
  1. **ニーモニック解析**：`mov`, `push`, `add`, `call` などの命令パターン認識。
  2. **ModR/M バイトの計算**：レジスタやメモリの指定方法（`[ebp-4]` など）に応じて複雑に変化する x86 特有のバイナリ表現（ModR/M, SIB）を組み立てる。
  3. **シンボルテーブル作成**：ラベル（`_main:` など）のアドレスを記録し、COFF 形式のヘッダーと一緒に書き出す。

### 3. コンパイラ（Compiler）

最後になるのがコンパイラーだ。ActiveBasic の文法（AST：抽象構文木）を解析して、アセンブリ言語を出力する司令塔。実は一番難易度が高い。最初からコンパイラーを完全なものにしようとすると挫折する。

## 自作ツールチェーンの全貌

今回はすべてのツールチェーンを ActiveBasic で自作する。データの流れは以下のようになる。

```text
[ ActiveBasic ソース (.ab) ]
           │
           ▼  ＜ 1. ABコンパイラ (名称abc) ＞
[ x86 アセンブリテキスト (.asm) ]
           │
           ▼  ＜ 2. ABアセンブラ (名称abassembler) ＞
[ COFF オブジェクトファイル (.obj) ]
           │
           ▼  ＜ 3. ABリンカ (名称ablinker) ＞
[ Windows PE 実行ファイル (.exe) ]
```

これに加えて **abpc**（`actb32.exe` に名称変更）を作成した。abc は `.abp` ソース 1 ファイルのみをコンパイル可能なのだが、abpc は `.pj` ファイルを読み込み、複数のソースが入っているプロジェクト全体をビルドできる。

## 開発手順

1. **リンカーを自作する**
   NASM 等の既存ツールが出力した `.obj` を自作リンカに読み込ませ、自分で PE ヘッダーを組み立てて `.exe` を吐き出させる。リンカーを自作すると「Windows で動くバイナリの仕組み」が完全に理解できるようになる。
2. **アセンブラを自作する**
   手書きの `.asm` を読み込み、x86 マシン語に変換して自作リンカが読める `.obj` を吐き出す。
3. **コンパイラーを育てる**
   ActiveBasic の構文解析を強化していき、自作アセンブラへテキストを渡す。

この順番で開発を進めることにした。

まずはリンカーを自作するのが目標だが、いきなり作り始めると挫折してしまう。最初に **coffdump** を作ることになる。

## coffdump からリンカーへ

coffdump をリンカーに成長させていく。coffdump で COFF ファイルの読み込みまで完了しているので、あとは PE ファイルを出力するだけだ。

### リンカーの核心：「リロケーション」

アセンブラが作った `.obj` の時点では、例えば `call _ExitProcess` の呼び出し先アドレスは `00 00 00 00`（ダミー）になっている。これを正しいアドレスに書き換える作業が **リロケーション（Relocation）** だ。

```text
【.objの中身】
  E8 00 00 00 00   ; call 0x00000000 (アドレス未定)

【リンカーの計算】
  1. _ExitProcess の実際の配置アドレスを計算 (例: 0x00402000)
  2. relative_offset = 目的地のRVA - (今の命令のRVA + 5)
  3. 差分アドレスを計算してバイナリを書き換える

【.exeの中身】
  E8 1B 10 00 00   ; call 0x0040201B (本物のアドレスに補正完了！)
```

`coff.abp` に定義を追加する。

#### ③ 書き換え指定情報

```vb
' --- 3. COFF Relocation (書き換え指定情報) = 10バイト ---
Type COFF_RELOCATION
    VirtualAddress   As DWord  ' 補正対象のオフセット
    SymbolTableIndex As DWord  ' どのシンボルを参照しているか
    RelType          As Word   ' REL32(相対) か DIR32(絶対) か ※Typeは予約語のため別名
End Type
```

#### ④ シンボルテーブル

```vb
' --- 4. COFF Symbol (シンボルテーブル 1エントリ = 18バイト) ---
Type COFF_SYMBOL
    Name(7)            As Byte   ' 短い名前 / 先頭4バイトが0なら文字列テーブル参照
    Value              As DWord
    SectionNumber      As Word   ' 1始まり。0=未定義, FFFF=絶対, FFFE=デバッグ
    SymType            As Word   ' ※Typeは予約語のため別名
    StorageClass       As Byte
    NumberOfAuxSymbols As Byte
End Type
```

### PE フォーマット（.exe）の組み立て方

リンカーは、補正が終わったマシン語（`.text`）の前に PE ヘッダーをガッチャンコして `.exe` を作る。`.exe` のバイナリ構造は以下の並びになる。

```text
┌─────────────────────────────────────────┐
│ 1. DOS Header & DOS Stub                │  ' "MZ" から始まる昔の名残 (64〜128バイト)
├─────────────────────────────────────────┤
│ 2. PE Signature ("PE\0\0")              │  ' 4バイト
├─────────────────────────────────────────┤
│ 3. PE File Header                       │  ' COFFヘッダーと同等 (20バイト)
├─────────────────────────────────────────┤
│ 4. PE Optional Header                   │  ' エントリポイント(実行開始位置)や
│                                         │    ImageBase(基本ロードアドレス
│                                         │    0x00400000)
├─────────────────────────────────────────┤
│ 5. Section Headers                      │  ' 各セクションのアドレス・サイズ定義
├─────────────────────────────────────────┤
│ 6. Section Data (.text, .data, etc)     │  ' 補正済みのマシン語バイナリ
└─────────────────────────────────────────┘
```

> 💡 **コツ：アライメント（配置）に注意**
> Windows の PE 形式では、セクションのサイズや配置アドレスを **512 バイト（ファイル上）** や **4096 バイト（メモリ上）** の倍数にパディング（0 埋め）して揃える必要がある。

## 自作リンカー開発のステップ

いきなり DLL のインポート（`kernel32.dll` の結合など）までやろうとすると大変なので、段階を踏んで実装する。

1. **.obj ファイルのダンパーを作る**（バイナリ解析の練習）
   自作または NASM が出力した `.obj` を読み込んで、ヘッダー情報や `.text` のマシン語（16 進数）を画面に表示するツールを作る。こちらは coffdump で完了しているので、プロジェクトをコピーする。
2. **ヘッダーテンプレートを使って .exe を吐く**（固定ヘッダーの複製）
   ダミーの PE ヘッダー（あらかじめ正常な EXE から抜き出したバイナリ）の末尾に、`.obj` から取り出した `.text` をそのまま貼り付けて `.exe` を生成してみる。
3. **PE ヘッダーを自前で計算して組み立てる**（動的生成への移行）
   エントリポイント（`AddressOfEntryPoint`）やセクションサイズを `.obj` の値から正しく計算して、PE ヘッダー構造体を構築する。
4. **単一ファイルのリロケーション処理を実装**（アドレスの結合）
   `.obj` 内のリロケーションテーブルを読み込み、`call` や `jmp` の相対アドレス補正を正しく計算して上書きする。
5. **外部 DLL（IAT：Import Address Table）の構築**（完成！）
   `ExitProcess` などの Win32 API を呼べるように、`.idata`（インポートセクション）を自力で構築して PE に追加する。
