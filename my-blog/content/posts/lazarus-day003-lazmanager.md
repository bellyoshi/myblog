# LazManager - LazbuildをGUIで操作するアプリ - Day3

Lazarusチャレンジ3日目です。今回は、 **LazbuildをGUIで操作するアプリ「LazManager」** を作成することにしました。

## 今回の目標

Day2の開発を通じて、Lazarusプロジェクトをコマンドラインからビルドする際に、毎回`C:\Lazarus\lazbuild`とフルパスを指定する必要があることに気づきました。また、プロジェクトの作成や管理をGUIで行えるツールがあれば便利だと考えました。

そこで今回は、以下の機能を持つLazManagerを開発することにしました：

- **設定画面**: Lazbuildのパス、エディタの設定、プロジェクトルートフォルダの既定値を設定
- **作成画面**: プロジェクトの新規作成（コンソール、単純なプログラム、アプリケーション）
- **起動画面**: エディタやコンソール、Lazarus IDE、エクスプローラーでプロジェクトを起動

## アプリの仕様

### 設定画面

以下の設定項目を用意します：

- **Lazbuildのパス**: コマンドラインからビルドする際に使用するlazbuildのパス
- **エディタ1のパスと名前**: Cursor用の設定
- **エディタ2のパスと名前**: VSCode用の設定
- **エディタ3のパスと名前**: Antigravity用の設定
- **プロジェクトルートフォルダの既定**: 新規プロジェクトを作成する際のデフォルトフォルダ

### 作成画面

プロジェクトを作成するための画面です：

- **プロジェクトルートフォルダ**: 設定画面で指定した既定値を初期表示
- **アプリ名称**: ローマ字で入力（プロジェクト名として使用）
- **アプリの種類**: ラジオボックスで選択
  - コンソール
  - 単純なプログラム（lprのみ）
  - アプリケーション（Winアプリ）
- **作成ボタン**: 押下すると、プロジェクトルートフォルダ＋アプリ名フォルダを作成し、そのフォルダにlazbuildで初期プロジェクトを作成

### 起動画面

作成したプロジェクトを起動するための画面です：

- **エディタの起動**: 設定したエディタの名前を表示し、そのフォルダで起動可能
- **コンソールの起動**: そのフォルダでコマンドプロンプトを起動
- **LPIファイルの起動**: Lazarus IDEでlpiファイルを開く（デフォルトアプリで起動）
- **エクスプローラーの起動**: そのフォルダをエクスプローラーで開く

### 画面遷移

作成画面と起動画面は、同じフォーム上でコントロールの表示/非表示を切り替えることで実現します。プロジェクトを作成した後、自動的に起動画面に切り替わるようにします。

## Cursorに投げたプロンプト

プロジェクトを作成し、Cursorへ以下のプロンプトを投げました：

```
# 目的
Lazarus (Object Pascal) を使用して、Lazarusプロジェクトの作成・管理を効率化するGUIツールを作成したい。

# 動作環境・設定
- 言語: Object Pascal (Lazarus/LCL)
- Lazbuildのパス: C:\Lazarus\Lazbuild.exe (デフォルト値)
- 設定保存: TXMLPropStorage または TJSONConfig を使用して、exeと同じ階層のconfigファイルに保存する。

# UI構成 (TForm1)
1. **設定セクション** (TPageControlまたは別フォーム)
   - Lazbuildのフルパス入力 (TFileNameEdit)
   - エディタ1〜3の「名前」と「実行ファイルパス」の入力欄
   - 既定のプロジェクトルートフォルダ (TDirectoryEdit)

2. **メインセクション (作成・起動 兼用)**
   - **新規作成パネル**:
     - プロジェクト名入力 (TEdit: ローマ字)
     - プロジェクトルート選択 (TDirectoryEdit: 設定値を初期表示)
     - 種類選択 (TRadioGroup): 「コンソール」「単純なプログラム(lpr)」「アプリケーション(GUI)」
     - 「作成」ボタン
   - **起動・操作パネル**:
     - エディタ1〜3の名前が付いたボタン（設定から動的にキャプションを変更）
     - 「コンソールをここで開く」ボタン
     - 「Lazarus IDEで開く (.lpi)」ボタン
     - 「エクスプローラーで開く」ボタン

# 処理ロジックの指示
1. **作成ボタン押下時**:
   - `ForceDirectories` でフォルダを作成。
   - `TProcess` を使用して、以下のコマンドを実行してプロジェクトを生成する。
     - 例: `lazbuild --create-project=app [プロジェクト名].lpi` (種類に応じて引数を変える)
   - 成功したら、起動パネルを表示（または活性化）させる。

2. **エディタ起動**:
   - `TProcess` を使用して、設定されたエディタパスを実行する。その際、カレントディレクトリをプロジェクトフォルダに設定すること。

3. **LPI起動**:
   - `OpenDocument` (LCLIntfユニット) を使用して、システム既定のアプリで .lpi を開く。

# Cursorへの追加指示
- まず、これらを実現するためのユニット（MainForm.pas）のコード全体を生成してください。
- 各ボタンのOnClickイベントの実装を含めてください。
- Windows環境を前提としたパス処理にしてください。
```

## 発生した問題1: プロジェクトの作成ができない

まず、プロジェクトの作成からできない。Geminiに聞いてみる。

**lazbuildにcreate project機能はあるか。**

結論から申し上げますと、残念ながら **lazbuild 自体に「新規プロジェクトをゼロから作成する（Create Project）」という機能はありません。**

lazbuild はあくまで、既存のプロジェクトファイル（.lpi）やパッケージファイル（.lpk）をコマンドラインからビルド（コンパイル）するためのツールです。

**なにー。**

ということでCursorに追加の作業依頼。プロジェクト作成機能をLazManagerに実装することになりました。

## 発生した問題2: ビルド時に固まる

次にビルドをしようとしても固まるバグ。Geminiに相談。

**以下は不完全なLazarusのコードである。`Process.Execute;`で固まりアプリが動かなくなる。どうしてかを解説。**

Geminiの解説によると、問題の原因は**デッドロック（行き止まり）**の発生です。

### 固まる原因：パイプのバッファ溢れ

`TProcess` のオプションに `poWaitOnExit` と `poUsePipes` を同時に指定していることが原因です。

**パイプの仕組み**: `poUsePipes` を使うと、OSは実行したプログラム（lazbuild）の出力を一時的に保存する「バッファ（メモリ上の箱）」を用意します。

**バッファの限界**: この箱のサイズは有限です（通常数KB〜64KB程度）。プログラムの出力（ログなど）がこの量を超えると、OSは**「中身を読み取ってもらうまで、次の書き込みを待機（停止）」**させます。

**待ちぼうけ**: しかし、コードは `poWaitOnExit` を指定しているため、`Process.Execute` の行で「プログラムが完全に終わるまで」じっと待っています。

**デッドロック**: 
- lazbuild: 「ログが一杯だ。誰か読み取ってくれないと、これ以上進めない（停止）」
- あなたのアプリ: 「lazbuildが終わるまで、次の行（読み取り処理）には進まない（停止）」

結果、お互いが相手を待つ状態になり、永遠に固まります。

### 解決策

大きな出力を伴うビルド処理などでは、`Execute` を呼び出した後に、プロセスが動いている間、逐次的に出力を読み取る必要があります。

最も一般的で簡単な修正方法は、`TProcess` を継承して便利にした `RunCommand` 関数（Process ユニットに含まれる）を使うか、ループで読み取るコードに書き換えることです。

ということで、Geminiに完全なコードをお願いする。修正はあっという間に完了する。

## 発生した問題3: エディタ起動時のエラー

次にエディタを起動してみるが、パスも名前も「Cursor」としていたのだが、エラーコード2で動かない。こちらもGeminiに聞いてみる。

**以下は不完全なLazarusのコード。実行するとEProcess例外が発生。Failed To execute:2が発生する。パスは「Cursor」が設定されている。なぜかを解説。**

Lazarus（Free Pascal）の `TProcess` を使用して「Cursor」を起動しようとした際に `Failed to execute: 2` が発生する主な理由は、`TProcess` が Windows のシェル（コマンドプロンプトや環境変数）を経由せず、直接バイナリを叩こうとしているからです。

エラーコード「2」は、OSレベルの **「指定されたファイルが見つかりません（File Not Found）」** を意味します。

### TProcess は PATH を自動補完しない

`TProcess` は、実行ファイル名だけ（例：「Cursor」）を指定しても、Windowsの環境変数 `PATH` を参照して自動的にフルパスに変換してくれる機能がありません。そのため、実行ファイルのフルパスを指定する必要があります。

### 解決策：cmd /c を介して実行する（推奨）

`cmd /c` を使う方法でメソッドの完全なコードを出してくださいとお願いする。

そうすると、今度は動きました。

## 学んだこと

Day3の開発を通じて、多くのことを学びました：

### ツールの機能について

- **Lazbuildにはプロジェクト作成機能がない**: ビルド専用のツールであることを理解した
- **プロジェクト作成は自分で実装する必要がある**: .lpiファイルや.lprファイルを手動で生成する必要がある

### 技術的な学び

- **TProcessのデッドロック問題**: `poWaitOnExit` と `poUsePipes` を同時に使うと、バッファ溢れでデッドロックが発生する
- **出力の逐次読み取り**: 大きな出力を伴う処理では、プロセス実行中に逐次的に出力を読み取る必要がある
- **TProcessとPATH**: `TProcess` は環境変数 `PATH` を自動補完しないため、フルパスを指定するか、`cmd /c` を介して実行する必要がある

### アイコン作成の学び

- **AIによるアイデア出し**: Geminiにアイデアを考えてもらうことで、自分では思いつかないデザイン案を得られた
- **プロンプトの重要性**: 「ナイト」と「チーター」の違いを明確に指定することで、希望通りのアイコンを生成できた
- **画像からアイコンへの変換**: 画像生成AIで作成した画像を、専用ツール（@icon変換）で.icoファイルに変換する必要がある
- **デザインの意味**: ナイトと歯車の組み合わせが、「プロジェクトを動かすエンジン」というコンセプトを視覚的に表現できた

### 問題解決のプロセス

- Cursorに依頼しても、すべてが完璧に動くとは限らない
- Geminiは問題の原因を詳しく解説してくれるので、技術的な理解を深めるのに有効
- 複数のAIツールを使い分けることで、効率的に問題を解決できる
- アイコン作成でも、AIにアイデアを考えてもらい、生成してもらい、変換方法を教えてもらうという一連の流れで完成させることができた
